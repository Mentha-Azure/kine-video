# 设计取舍

本文回答「为什么这么设计」。README 回答「是什么、怎么用」，这里记决策依据与代价。

每一条都写成「选了 A，因为 B，代价是 C」——代价写出来，方便判断某个约束是不是该被绕开。

---

## 一、把「第 N 帧 = f(N)」当地基

所有能力都是从这一条推出来的：

| 因为每帧可独立重算 | 才能做到 |
|---|---|
| 帧之间无依赖 | 4 个 worker 并行抓帧，产物与单 worker 逐字节一致 |
| 给定 T 就能算出画面 | 跳帧抽检、单片重抓、任意位置 `probe` |
| 同一输入必得同一输出 | 内容寻址缓存、specHash 作工程身份、基线回归 |
| 渲染是纯函数 | 两次渲染 `--no-cache` 产物 sha256 相同（`tools/repro-check.ts`） |

**代价**：画面代码里不能有 `Math.random`、跨帧累积状态、墙钟时间、CSS 自走动画。这四条由 `audit` 扫描源码强制（`L-PURE-001..004`）。

对一个动画师来说这是很硬的约束——很多「手感」靠的正是帧间残留。取舍在于：**可复现、可测量、可并行**换掉了**一部分表达自由**。想表达随机感，用 `rng(通道名, index)`：它按索引返回确定值，看起来随机，但每帧可重放。

## 二、AI 是首要用户，人类是第二用户

AI 的工作方式是「读事实 → 改声明 → 量结果」，不是「拖一个块到轨道上」。所以接口形态跟着变：

- **所有能力走 CLI 子命令 + MCP 工具**，返回结构化 JSON：`{ ok, tool, data, verdict, facts, hints, nextActions }`。`facts` 是可以直接引用的实测数据，`nextActions` 是建议的下一步。
- **歧义不猜**。`find` 命中多个候选时返回 `AMBIGUOUS` 并列出候选与实测参照值，等调用方显式指定。这条来自源项目最贵的一次返工：改错了同名元素，四轮。
- **改动走事务**。`edit --tx --quote "用户原话"` 会写 changelog、留备份、可 `rollback`。谁在什么语境下改了什么，事后能查。
- **人类界面退化为「看片 + 看历史」**：3–5 秒成品形态短预览（`preview`）+ 变更记录（`changelog`）。

**代价**：没有时间线缩略图、没有波形拖拽、没有实时预览窗口。调整一个 0.1 秒的节奏要改数值再重渲。

## 三、不做拖拽实时编辑 UI（非目标）

实时编辑与逐帧确定性是两种架构：

- 实时编辑要增量状态——改了什么就重算什么，靠 UI 状态树维持一致性。
- 确定性渲染要全量重算——第 N 帧只依赖 T 与工程声明，不依赖「上一帧画了什么」。

硬把两者塞进一个引擎，会得到「实时预览和最终成片不一致」这类最难查的问题。

所以 Kine 明确放弃前者。**代价**是上手门槛：你得接受「改 YAML → 跑命令 → 看输出」的循环，而不是拖着玩。

## 四、把审美写成 lint 和指标

「这里看着有点灰」「节奏有点拖」这类判断无法验收，也无法回归。做法是把它们翻译成可计算的量：

| 主观描述 | 量化成 | 判定 |
|---|---|---|
| 画面发灰 | 最暗 30% 像素的 RGB 均值 | 必须落在 6–9 |
| 太空 | 灰度 >40 的像素占比 | ≥ 0.9% |
| 死板 / 没动 | 相隔 0.4s 两帧的像素差占比 | ≥ 4%（工程可声明更低） |
| 抖得难受 | 相机位移的解析复算 p99 | ≤ 2px |
| 贴边被切 | 最外 34px 环带的内容占比 | ≤ 0.6 |
| 转场卡顿 | 孤立跳变（本帧差 > 邻域均值 ×2.2） | 0 命中 |

配套 70 条 lint 规则（`kine rules` 可逐条查含义与修法），在 `audit` 阶段拦下。

**代价**：默认风格被约束得很死——唯一强调色 `#ff2e3f`、暗角 ≤0.90、白闪 ≤0.085、全站等宽字体。这些数字来自源项目踩过的坑（灰白病、全屏红板、贴边 HUD 被切），不是审美偏好。

**出口**在 v2 之后打开：`theme.profile: core|extended|free` + 色板库，允许按工程覆盖配色与后处理上限，但纯函数与时间模型不可动。

## 五、`video` 图层直接报错，而不是"尽力而为"

`kind: video` 会在 audit 阶段报 `E-ASSET-002`，不是没实现，是明确拒绝。

原因：视频解码结果依赖解码器版本、色彩管理、丢帧策略。同一份 mp4 在两台机器上解出来的第 100 帧可能差几个像素——这会直接摧毁「字节级复现」这个地基。

可选方案（按帧预转 PNG 序列）本质上是把视频变成图片序列，那就该用 `image` 图层。

**代价**：不能直接剪实拍素材。**收益**：不会出现「本地好好的，CI 上差三帧」这类查不动的问题。宁可报错，不要静默失败——同一条原则也用在缺资产（`E-ASSET-001` + 贴屏横幅）、音频混音失败（`E-AUDIO-MIX-001`，拒绝产出无声成片）。

## 六、三层哈希为什么分开

| 哈希 | 覆盖范围 | 用途 |
|---|---|---|
| `specHash` | 归一化后的 IR（含被引资产 sha256） | 工程身份：缓存目录、基线、回归的根键 |
| `visualHash` | 只含影响像素的部分 | 帧缓存键——**改音频不重渲帧** |
| `stateHash` | 单帧的场景/镜头/相机/元素盒/测量 | 黄金帧回归，跨会话可复现 |

如果只有一个哈希，改一下音乐音量就得重渲全片。拆开之后，音频改动只重建音频缓存，帧缓存直接复用。这个拆分在 v5 的冒烟里验证过：图片资产注入后 `specHash` 变了，`visualHash` 零变化，分片缓存全部命中。

跨版本还需区分「引擎升级」与「工程被改」：`HASH_SCHEME`（IR 规范形式版本）与 `RENDER_VERSION`（像素行为版本）显式进入哈希输入。升级导致首次全量重渲时，能从标记上看出原因。

## 七、明确不做的事

- **不做 NLE 时间线 UI**：见第三节。
- **不做视频素材解码**：见第五节。
- **不做云端协作 / 多人在线**：单一真源是本地文件，事务与锁都基于文件系统。
- **不做通用节点式合成图**：DSL 是「幕 → 镜头 → 图层」的固定三层，够表达 MV、讲解片、信息片，不做任意拓扑。
- **不做插件市场**：widget 扩展走 `registerWidget` + 类型校验，社区分发靠 npm 包，不建中心化市场。
